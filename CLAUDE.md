# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

FreeTheLights is a SimHub plugin (.NET Framework 4.8, WPF). It drives the LEDs of wheels, dashboards, LED bars and LED flags (including illuminated buttons, lights and dials on a wheel's front plate) with five features:
- car-specific RPM lights from [lovely-car-data](https://github.com/Lovely-Sim-Racing/lovely-car-data)
- race control flags
- car proximity
- ABS
- traction control

SimHub's SDK samples, the reference for plugin APIs, are in the `PluginSdk\` folder of the SimHub install.

## Branches and commits

Follow `CONTRIBUTING.md`: develop every change on its own branch off `main` (never commit to `main` directly), as isolated, self-contained commits (one logical change each, each one building and passing the tests), with Linux-style messages (`<area>: <imperative summary>`, a body explaining what and why, wrapped at 72 columns).

## Build and test

Build with MSBuild from Visual Studio or the Build Tools, not `dotnet build`: the projects use the classic (non-SDK) csproj format, as SimHub's SDK samples do.

```bash
MSBUILD=msbuild   # or the full path to Visual Studio's MSBuild.exe
"$MSBUILD" FreeTheLights.sln -restore -nologo -v:m -p:DeployToSimHub=false

XUNIT="$HOME/.nuget/packages/xunit.runner.console/2.9.3/tools/net48/xunit.console.exe"
"$XUNIT" tests/FreeTheLights.Tests/bin/Debug/FreeTheLights.Tests.dll -nologo -noshadow
"$XUNIT" tests/FreeTheLights.Tests/bin/Debug/FreeTheLights.Tests.dll -class FreeTheLights.Tests.WizardTests
"$XUNIT" tests/FreeTheLights.Tests/bin/Debug/FreeTheLights.Tests.dll -method FreeTheLights.Tests.FrameRendererTests.Matrix_patterns
```

- **Scripts:** `sh tools/dev.sh build|test|deploy` runs the commands above (`deploy` is the build that copies the DLL into SimHub; the others never deploy).
- **Restore:** pass `-restore` after any csproj change, otherwise NuGet fails with a "RuntimeIdentifier 'win'" error.
- **Deploying to SimHub:** without `-p:DeployToSimHub=false`, a build copies `FreeTheLights.dll` and its `.pdb` into the SimHub folder. That changes the user's SimHub install, the copy fails while SimHub is running, and it may need admin rights, so don't deploy unless asked.
- **SimHub DLLs:** they are referenced from `$(SIMHUB_INSTALL_PATH)`, or from the default install folder if that variable is unset, with `Private=False`.
- **Reference assemblies:** no .NET Framework 4.8 targeting pack is needed. The net48 reference assemblies come from the NuGet package `Microsoft.NETFramework.ReferenceAssemblies.net48`.
  - WPF compiles XAML through a temporary `*_wpftmp.csproj` project that doesn't get NuGet's imports.
  - The `TargetFrameworkRootPath` block near the end of `src/FreeTheLights/FreeTheLights.csproj` works around this. Keep it.
- **C# version:** `LangVersion` is 7.3. Don't use records, `init`, or other features that need newer runtime support.
- **Build warnings:** the build is expected to finish with zero warnings.
- **Line endings:** most files use CRLF; keep each file's line endings when editing (a script that rewrites a whole file must write them back the same way). Some older files are LF.
- **Tests:** `tests/FreeTheLights.Tests` (xunit 2.9.3, classic csproj: add new test files to it). One file per area: `FrameRendererTests` (features and flags), `LedResamplerTests`/`CarDataTests`/`CarDataVersionTests` (RPM and car data), `LayoutTests`/`FrontPlateTests` (groups, elements, press colors), `InputStateTests` (input state), `SettingsTests` (persistence, enum pinning), `SettingsMigrationTests` (format migrations), `PresetTests` (SimHub presets, profiles, Connect), `DashPhotoTests` (dashboard pictures), `InspectorTests` (preview inspector), `PreviewLayoutTests` (where the preview draws the LEDs), `WiringTests` (wiring check), `WizardTests` (wizard steps, with a fake `IWizardHost`), `ButtonAssignmentTests` (the wizard's button assignment), `LedColorTests`, `UpdateTests` (release check and plugin update). Fixtures (car files, one settings file per format) in `Fixtures/`.
- **Development tools** (`tools/`, see `tools/README.md`): a UI harness that renders the settings page, the wizard and dialogs off-screen to PNG files (with selectable presets and inspector selections), and the dashboard probe that maintains `DashboardLayouts.json`. Build them with `sh tools/build.sh` after the solution.
- **Releases** (`CONTRIBUTING.md`, "Releases"): `tools/release.sh` builds and tests `main`, tags `vX.Y.Z` (the version in `AssemblyInfo.cs`) and creates the GitHub release with `FreeTheLights.dll`, `FreeTheLights.dll.sha256` and notes generated from the merged pull requests (`.github/release.yml`). It publishes to GitHub: only run it when asked.

## Architecture

### Data flow
```
SimHub game loop → FreeTheLightsPlugin.DataUpdate
   → BuildSnapshot (GameReaderCommon.StatusDataBase → Core/TelemetrySnapshot; iRacing's debris flag from its raw session flags;
     the shared Core/InputState, fed by PluginManager.InputPressed/InputReleased, also outside a game)
   → Engine/TestMode.Apply (simulated inputs from the test chips, OR-ed into the telemetry)
   → per render copy of a DeviceConfig (Settings/DeviceSnapshot), per DevicePart: Engine/FrameRenderer.Render → LedColor[] frame (physical LED order of the part's channel)
     (or Engine/WiringPattern.Render for the part whose wiring is being checked, TestMode.WiringPartId)
   → Engine/FrameStore (frame per part, with the time it was rendered)
SimHub LED editor → Effect/FreeTheLightsEffect (LED strips) or FreeTheLightsMatrixEffect (LED flags), storing DeviceId + PartId
   → reads the part's frame via the static FreeTheLightsPlugin.Instance (FindPart: empty/unknown part = first part) → SimHub's drivers talk to the hardware
```
- **Hardware output:** the plugin never talks to hardware. The user adds the FreeTheLights effect to the LED profile of each SimHub channel of a device (shift lights, buttons, ...), and picks the part for that channel.
- **Transparent LEDs:** transparent entries in a frame (alpha 0) let effects below FreeTheLights in that profile show through.
- **`DataUpdate`:** it is on SimHub's critical path. It must not block or throw. Each part renders in its own try/catch, and errors are logged at most every 10 s (`LogErrorThrottled`).
- **Frame age:** `FrameStore` returns no frame once it is older than 1 s (`MaxAgeMs`), so the effects release the LEDs (transparent) instead of freezing on the last frame when `DataUpdate` stops, fails before rendering, or a part keeps failing.
- **Same colors, same array:** a frame with the same colors as the part's previous one keeps the previous array (with the new time), so a new array means new colors and readers that compare references (the previews) only repaint on a change. Never modify a frame array.
- **Render copies:** DataUpdate and the LED effects never read the live settings, which the UI edits. They read `RenderDevices` (`Settings/DeviceSnapshot`): JSON copies of the saved devices (plus the device being set up in the wizard, `WizardDevice`) that `Init`, the settings page's timer and the wizard publish (`PublishDevices`) when something changed. Never modify a render copy.

### Keep SimHub types out of the logic
`Core/`, `Settings/`, `Engine/`, `CarData/` and `Updates/` do not reference SimHub types. The test project relies on this: it loads `FreeTheLights.dll` without SimHub present. SimHub types belong only in `FreeTheLightsPlugin.cs`, `Effect/`, `SimHubData/` and `UI/`, and are translated at that boundary (`TelemetrySnapshot`, `SimHubDeviceInfo`/`SimHubButtonLayout`, and `LedColor` ↔ `System.Drawing.Color`). Keep logic that only needs SimHub's JSON in `Settings/` (`ShDeviceParser`, `SimHubProfiles`) so it can be tested.

### LED model
- **Device and parts:** a `DeviceConfig` is one card in the device list (name, enabled, type, optional SimHub preset). It holds one or more `DevicePart`s, one per SimHub LED channel (`LedChannel`: Leds, Buttons, Encoders, Matrix). Each channel has its own LED profile in SimHub, numbered from LED 1.
  - Parts are fully independent: each has its own groups, features, layer priority and brightness. Everything below about groups, features and layers is per part.
  - The settings page shows a part switcher above the feature tabs when a device has more than one part.
- **Device type:** `DeviceConfig.Type` (`DeviceType`: Custom, Wheel, Dashboard, LedBar, LedFlag) is set by the wizard and fixed afterwards (the device header only shows it); a different kind means adding the device again. It only affects how the device is previewed (`UI/PreviewLayout.cs` places the LEDs, `UI/LedPreview.cs` draws them): a wheel from a SimHub preset on SimHub's photo, a dashboard from a SimHub preset on its product picture (`SimHubPreset.ShowsLedsOnPhoto`), other wheels on a generic GT wheel, other dashboards on a generic dash, the rest as a labelled schematic.
- **Group:** a `DevicePart` holds `LedGroup`s: HorizontalRow, VerticalColumn, Matrix or Element. Each group occupies `[StartIndex, StartIndex + LedCount)` of the part's physical LED strip.
- **Logical coordinates:**
  - Rows: index 0 is the leftmost LED.
  - Columns: index 0 is the bottom LED.
  - Matrices: (0,0) is top-left.
  - `LedGroup.PhysicalIndex(...)` maps these to the strip, handling `Reversed`, `Serpentine` and `StartsAtBottom`. Features always work in logical coordinates.
- **Features:** each feature (`Settings/FeatureSettings.cs`) has `TargetGroupIds` and `AllowedKinds`/`DefaultKinds`. `DevicePart.AddGroup` assigns the next start index and auto-targets the new group for features whose `DefaultKinds` match. RPM only drives rows.
- **Front plate elements** (`LedGroupKind.Element`):
  - Each element is exactly one LED: a Button, Light or Dial (`ElementType`).
  - Elements are not added one by one. They are created and removed by `DevicePart.ApplyFrontPlate(dialPresetId, sidePresetId)` from the presets in `Settings/FrontPlatePresets.cs`, or copied from a SimHub button layout (`PresetBuilder`). The preset ids are persisted, so never change them.
  - Elements from a SimHub layout have `PhotoX`/`PhotoY`/`PhotoSize` (`HasPhotoPosition`) and `StartIndex` = SimHub's LED number − 1. Their position and LED number are fixed: `PackStartIndices` and wiring reorders skip them, and the inspector hides their LED index (the subtitle shows the number).
  - Dials have `Side` None and sit in the center; buttons and lights are Left/Right. `ElementSlot` is the position within the preset, and right slot *k* mirrors left slot *k*. Settings are independent per element.
  - An element shows **at most one effect**: Flags, Proximity, ABS or TC, never RPM. Always change it through `GetElementEffect`/`SetElementEffect`; `EnsureDefaults` repairs elements that have several.
  - When no effect lights an element, it shows `LedGroup.StaticColor` through the lowest layer, `LayerKind.StaticColor` (`StaticColorSettings`, which targets every element).
  - While one of its inputs is pressed, a button or dial shows `LedGroup.PressColor` through `LayerKind.Press` (`PressSettings`, which also targets every element; first in the default priority). Inputs are SimHub input names, explicit per type: `LedGroup.InputSlots` (`InputSlot`) is the one place that says which inputs an element has, and `GetInput`/`SetInput` map a slot to its persisted property. A button has exactly one (`ButtonInput`), a dial one per direction (`ClockwiseInput`, `CounterClockwiseInput`), a light none (`CanBePressed`). The renderer and the inspector both go through the slots. The press color is not an effect: it doesn't count towards the one-effect rule.
  - The UI keeps elements out of the feature target chips; they are edited by clicking them in the live preview (the inspector panel, see UI), not in a table.
- **Layer composition (`FrameRenderer`):** each enabled feature renders its own layer. Per LED, the first non-transparent layer in `DevicePart.LayerPriority` wins, and the part's brightness is applied after that.
  - Use `LedColor.Off` (opaque black) when a feature wants an LED dark, for example in a blink off-phase or as a flag's "off" second color. Off keeps the LED owned, so lower layers don't flicker through.
  - Use `LedColor.Transparent` for "not mine".

### Features (`Settings/FeatureSettings.cs`, rendering in `Engine/FrameRenderer.cs`)
- **Adding a feature:** a settings property on `DevicePart` (repaired in `EnsureDefaults`), an entry in `DevicePart.AllFeatures` (with a new `LayerKind` value), its renderer in `FrameRenderer.Renderers` and, if it can drive rows, columns or matrices, a tab with target chips (`DeviceViewModel.TargetsOf`). `FrameRendererTests.Every_feature_has_a_renderer` and `FrontPlateTests.Every_feature_for_rows_columns_or_matrices_has_target_chips` fail until the last two exist.
- **RPM** (`RpmSettings`, rows only): car data from lovely-car-data (below); without it a generic green/yellow/red bar (`RpmFallbackMode`, first LED at a % of the redline, redline blink).
- **Flags** (`FlagSettings`): an ordered list of `FlagRule`s, one per `FlagKind`; the first enabled rule whose flag is active wins (`FrameRenderer.ActiveFlag`). Each rule has color 1, an optional color 2 (`""` = single color), a `FlagPattern` (how two colors are arranged; matrices get checkerboards/diagonals) and a `FlagAnimation` (steady, blink, swap colors). `FlagSettings.DefaultOrder` is the default priority; `EnsureDefaults` adds rules for new kinds.
  - Flag sources: Yellow, Blue, White, Black, Checkered, Green and Orange (meatball) come from SimHub's common `Flag_*` telemetry (Black does exist there). **Debris** has no common field: `FreeTheLightsPlugin.IsIRacingDebris` reads `DataCorePlugin.GameRawData.Telemetry.SessionFlags` while iRacing runs and `Core/IRacingSessionFlags` decodes bit `0x40`; other games never report it.
  - `FlagKind` value 3 was the removed black/white flag; don't reuse it.
- **Proximity** (`ProximitySettings`): the spotter's car left/right; rows fill from the side of the other car, columns per `FillOrigin`; optionally more LEDs the closer the car (`SpotterCar*Distance`, in meters; 0/NaN = unknown → all LEDs). Left/right elements react to their side, dials to both.
- **ABS / TC** (`IndicatorSettings`): lit while active; `PluginSettings.IndicatorHoldMs` holds single-frame activations.
- **Static colors** (`StaticColorSettings`): the elements' own colors, lowest layer; switched per part in the inspector.
- **Press colors** (`PressSettings`, front plate elements only): an element's `PressColor` while the input of one of its `InputSlots` is held. Buttons show it exactly while held. Dials show it for at least `PressSettings.DialMinimumOnMs` (50 ms) after each step (`InputState.IsHeldOrPressedWithin`, press times from the game loop's clock), because an encoder step can be pressed and released within one game loop frame. Empty color or no inputs = no reaction; black turns the LED off.
  - Inputs: `Core/InputState` records SimHub's `PluginManager.InputPressed`/`InputReleased` (every input SimHub reads, mapped or not, with names like `JoystickPlugin.<device>_B05`). The events come on background threads, so it locks; SimHub ignores the handlers' return value. The snapshot carries the shared instance (`TelemetrySnapshot.Inputs`). Held inputs are cleared when a game starts or stops (`InputState.Clear`), so a release SimHub never reported (a wheel unplugged while a button was held) doesn't keep a press color on for good.
  - `EnsureDefaults` inserts a missing Press layer first in `LayerPriority` (other missing layers are appended), so settings saved before it get it on top.
- **Test mode** (`Engine/TestMode`, the settings page's Test chips): RPM sweep, every flag, car left/right with a simulated distance, ABS, TC, button press (`TelemetrySnapshot.SimulatePress`: every element with a press color shows it); plus `WiringPartId` for the wiring check. "Stop all tests" clears everything (`Clear`). `WiringPartId` is a boxed Guid swapped atomically because the game loop reads it.
- **Colors:** `Core/LedColor` (`#AARRGGBB`; `Transparent` = not mine, `Off` = opaque black). In the UI, `ColorPickerButton` binds `ColorHex`; with `AllowNone` an empty string means "no color".

### RPM / lovely-car-data
- **Car file format** (`CarData/CarLedProfile`): `ledColor` holds `#AARRGGBB` colors. `ledRpm` is an array of `{gear: int[]}` objects. In both, **index 0 is the redline** and indices 1..N are the LEDs. An RPM of 0 or a transparent color marks an unused LED: a gap in the car's row (e.g. the McLaren 720S GT3), which the RPM lights never light (transparent, also at the redline) and which keeps its place on the device.
  - A redline color overrides all used LEDs.
  - `redlineBlinkInterval` blinks the current state, even when the redline color is transparent.
- **Mapping to the device** (`Engine/LedResampler.ResampleLeds`):
  - More device LEDs than car LEDs: the car's LEDs are shown one to one in the middle of the row, the outer LEDs stay transparent (as close to the real car as possible). When the leftover count is odd, one LED is added in the center for symmetry: an odd car row shows its center LED twice; an even one gets an extra center LED that lights once both car LEDs next to it are lit, in the right one's color.
  - Fewer device LEDs: device LED j takes the car LED under its center, with mirror-symmetric rounding so symmetric car patterns stay symmetric, and a device LED whose center car LED is off shows the nearest lit car LED in its span, so no shift stage is skipped.
- **Loading** (`CarData/CarDataService`):
  - Find the file by **looking up the car id in `data/manifest.json`**. File names often don't match the normalized car id; the normalized id is only a fallback.
  - Downloads run on background tasks and are cached under `PluginsData/Common/FreeTheLights/cardata`, refreshed per `CarDataRefreshHours` and falling back to the cache when offline. Only JSON objects are cached; writes go through a temp file, a failed write is only logged, and a corrupt cache file is deleted and downloaded again. Manifest paths that would leave the cache folder are rejected.
  - `CarDataVersion` reports which data is used: the format version from `changelog.md`, plus the branch and the last data commit from the GitHub API.

### Plugin updates (`Updates/`)
- **Check** (`UpdateService`): asks GitHub's API for the latest release of `Grollo13/FreeTheLights` (`releases/latest`, which skips drafts and pre-releases) on a background task, cached in `PluginsData/Common/FreeTheLights/update/latest.json` and asked at most once a day unless forced; offline, the cached answer is used. A release is offered when its tag `vX.Y.Z` is newer than the assembly version (`ReleaseInfo.IsNewerThan`, X.Y.Z.0 = X.Y.Z).
- **Install** (`UpdateService.Install`, `UpdateInstaller`): downloads `FreeTheLights.dll` and `FreeTheLights.dll.sha256` into the `update` folder, checks the hash and that the file is the FreeTheLights assembly of the release's version (`AssemblyName.GetAssemblyName`, nothing is loaded), then renames the running DLL to `FreeTheLights.dll.old` (Windows allows renaming a loaded DLL, not overwriting it; `.1.old` ... while an older one is still loaded) and copies the new one in its place. SimHub loads it at its next start; `Init` deletes the old files (`CleanupAfterUpdate`). Without write access to SimHub's folder (Program Files) the same steps run as an elevated PowerShell script (`IElevatedRunner`, a UAC prompt). Any failure leaves the old plugin in place.
- **UI:** the update card in the settings page's sidebar (above the car data card) shows the version and the update state (`SettingsViewModel.RefreshUpdateStatus`, from the 10 Hz `RefreshStatus`), the "Update plugin" button, "What's new" (the release page) and the "Check for updates" switch (`PluginSettings.CheckForUpdates`). The plugin checks at `Init` when it is on.
- **Trust:** only release downloads of that repository over https are accepted (`ReleaseInfo.IsTrustedAssetUrl`, checked on the resolved URL), and only its release pages are opened (`NotesUrl`). Never relax these.

### Settings persistence
- **Storage:** settings are stored with SimHub's `ReadCommonSettings`/`SaveCommonSettings`, which use Newtonsoft.Json.
- **Collections:** use `[JsonProperty(ObjectCreationHandling = ObjectCreationHandling.Replace)]` on every collection property. Never pre-fill defaults in constructors, or deserialization appends duplicates. Defaults are added afterwards by the `EnsureDefaults()` chain (`PluginSettings` → `DeviceConfig` → `DevicePart` → `FlagSettings`).
- **Migrations (`Settings/SettingsMigrator`):** the plugin reads the saved settings as a `JObject` (`ReadCommonSettings<JObject>`), and `SettingsMigrator.Load` migrates the JSON step by step from its `SettingsVersion` to `PluginSettings.CurrentVersion` before deserializing it. Saved settings that were migrated or replaced by defaults are first copied to `PluginsData/Common/FreeTheLights/backups/settings-v<version>-<time>.json`.
  - **When the format changes** (a property renamed, moved or reinterpreted, an enum value changed): bump `CurrentVersion`, add a `SettingsMigration` from the previous version to `SettingsMigrator.Migrations` (it edits the JSON, so the settings classes keep no legacy properties), and add the fixture `tests/FreeTheLights.Tests/Fixtures/settings-v<new>.json` (a serialized `PluginSettings` with the same content as the older fixtures). `SettingsMigrationTests` fails until all three are done. Never edit an existing step or fixture.
  - Purely additive changes (a new property with a default, a new enum member) need no new version: missing properties keep their defaults and `EnsureDefaults` repairs the rest.
  - Settings older than `SettingsMigrator.OldestMigratableVersion`, saved by a newer plugin (`TooNew`), or failing to load are replaced by defaults (logged as a warning). Raise `OldestMigratableVersion` only to drop old formats on purpose.
- **Format version:** `PluginSettings.SettingsVersion`; a saved file without one reads as 0 (too old).
- **Enum values are persisted as numbers.** Every enum stored in the settings has explicit values, pinned by `SettingsTests.Persisted_enum_values_never_change` (`LayerKind`, `LedGroupKind`, `ElementType`, `DeviceType`, `LedChannel`, ...). Don't renumber them within a format version; give a new member a new number and a test row.

### UI (WPF inside SimHub)
- **UI texts:** written for drivers setting up their devices. Say only what they need to do or know, in a sentence or less; no internals of FreeTheLights or SimHub (channels, start indices, the LED strip, car data sources, backups). Explanations go into tooltips, and every control and setting gets a short one.
- **View models:** settings objects are bound directly. They derive from `Core/ObservableObject`; PropertyChanged.Fody is not used.
- **Theme:** SimHub provides the MahApps.Metro theme at runtime (its `App.xaml` merges MahApps Controls/Fonts/Colors/Blue/BaseDark and `SimHubStyles.xaml`). Use SimHub buttons (`SHButtonPrimary`, `SHButtonSecondary`) and `mah:NumericUpDown`.
- **Shared look (`UI/Theme.xaml`):** cards, toggle switches (`Switch`), chips (`Chip`, `ChipCheck`, `ChipButton`), icon buttons, dialog buttons (`DialogButtonPrimary`/`DialogButtonSecondary` with `ButtonContent` + `ButtonIcon` inside, so every text button of the wizard and dialogs has the same size), icon tiles, feature headers and the icon tabs (`NavTabControl`/`NavTab`). The settings page, the wizard and the effect editor merge it. Feature accent colors live in `UI/Theme.cs` (`{x:Static ui:Theme.Rpm}`), so a feature looks the same everywhere.
  - **Icons:** Material icons from `MahApps.Metro.IconPacks.Material`, which ships with SimHub (referenced with `Private=False`). Check that an icon name exists in that version before using it. Keep icon types out of view models: the tests load `DeviceViewModel` without SimHub.
  - **`Ux` attached properties** (`UI/Ux.cs`): `Ux.Icon`, `Ux.Accent`, `Ux.Status` (on/off dot of a tab) and `Ux.Description` feed the templates.
  - **No prefixed attached properties in binding paths in Theme.xaml.** A path like `{Binding (ui:Ux.Accent)}` resolves `ui` against the file that uses the template, and in `DeviceWizard.xaml` `ui` is SimHub's namespace. Use `{TemplateBinding ui:Ux.Accent}` instead, or a trigger.
- **Custom styles:** they must use `BasedOn="{StaticResource {x:Type …}}"`. Without it, the implicit SimHub/MahApps style is lost and controls render white-on-white.
- **Drag & drop:** `UI/DragReorder.cs` is an attached behavior for vertical lists. Set `IsEnabled` on the ItemsControl and `Handle` on the grip. With `MoveCommand`, it sends a `MoveRequest` to the command; otherwise it calls `Move(int, int)` on the ItemsSource.
  - It doesn't use WPF's `DoDragDrop`. It captures the mouse, moves the dragged item with a `TranslateTransform`, animates the items it passes out of the way, and reorders the collection once, after the dropped item has slid into its slot.
  - Lists that are filtered or rebuilt on change (priority layers, the wiring list) need a `MoveCommand`: positions in the list are not indices in the underlying collection.
  - The item template's root should be a `Border`: the dragged item gets an opaque version of its background, so the rows below don't show through.
  - Reordering is drag-only; there are no up/down buttons.
- **Dialogs:** the new-device wizard (`UI/DeviceWizard`) is an `SHDialogContentBase`, opened with `ShowDialogWindowAsync`. Next/Back walk `ActiveSteps`. The steps are grouped by topic: the device (device, kind, connect), its LEDs (layout, positions, wiring), its buttons (front plate, inputs), then the summary. It doesn't ask for features: a new device has all of them on.
  - Step 1 is one searchable list: generic devices (templates) plus every SimHub device with LEDs, grouped by brand.
  - A SimHub device gets a kind step: SimHub has no device categories, so the user confirms the kind; `DeviceKindGuess` preselects a best guess.
  - **The device being built:** `DeviceWizardViewModel.Build()` returns the device the wizard will add. It is built again only when a choice changed (`LayoutChanged`, the name, the device or kind mark it dirty), so the later steps edit it in place (wiring, inputs). Every build keeps the same device and part ids and the parts' `SimHubProfileIds`: a profile set up in the wizard stays connected after going back to the layout.
  - **Steps on the real device** go through `UI/IWizardHost` (`SimHubWizardHost` in SimHub; tests and the harness use fakes; no host = the steps are skipped): their previews show the frame the game loop rendered for the device (`GetFrame`), so the patterns move in step with the device, and draw the pattern themselves only when there is none.
    - Connect (SimHub's LED profile): only for SimHub devices that are added in SimHub's Devices (`HasSimHubDevice`). It shows each part's connection state and connects every part with one click (`UI/WizardProfileStep`, the view model's `Profile`; `SimHubConnector.Connect`, as on the device page); once connected, the device breathes green while the step is open (`ShowConfirmationPattern` → `TestMode.ConfirmationDeviceId`, `Engine/ConfirmationPattern`), and so does the step's preview. It can be skipped. From this step on, the wizard's timer hands the device to the game loop (`FreeTheLightsPlugin.WizardDevice`, published with the saved devices by `PublishDevices` but never saved); closing the wizard clears it. Closing the wizard without "Add device", or picking other hardware, puts SimHub's settings back as they were before the first Connect (`UndoConnections`, from `SimHubConnector.Copy`), and other hardware gets new ids for the device and its parts.
    - LED wiring: only once a part with rows, columns or matrices is connected. It shows `WiringPattern` on that part (`ShowWiringPattern` → `TestMode.WiringPartId`, only while the step is open) and in a preview, in the wiring editor (`UI/WiringEditor`, shown by `UI/WiringEditorView` with its preview; the device page's wiring dialog uses the same): groups are added (row, or a column on the free side), removed and resized there, and dragged into order (`DevicePart.MoveWiring`); after each change `DevicePart.PackWiring` chains them again, and the step says how many of the channel's LEDs are in a group. This is where devices whose SimHub data doesn't tell the split (the generic Asetek device as a wheel: one 23-LED row) get their columns. The step also shows for a connected LED channel without groups.
    - Assign buttons: for devices with buttons or dials while SimHub's inputs are available. `UI/ButtonAssignment` asks for one input slot after the other and assigns the next input `InputState.Pressed` reports (handed to the UI thread with `Post`, with a session token as in the inspector). Inputs within 400 ms after an assigned one are ignored (`LockoutMs`: bounce, an encoder detent or one click reported under two names), so is the input just assigned when pressed again for the next prompt (Previous re-asks); an older input pressed for another button moves there. When connected, the device shows the button to press white and assigned ones green, through `ButtonAssignment.DisplayDevice` (a copy with only the static colors on).
  - The layout step only asks for LED counts (and a matrix' size). The groups get a default order; the wiring step (or the device page) fixes it.
  - The layout step exists for generic devices, LED flags and SimHub dashboards (to check the suggested split) until the dashboard's LED channel is connected: then the wiring step sets its groups, on the device as built (`HasLayoutStep`, `BuildsLayoutPart`). The LED positions step (SimHub dashboards with a product picture) also places the groups of the device as built (`PhotoGroups`), so going back from the wiring step shows its edits and moving LEDs keeps them; the generic drawing keeps their positions aside. The front plate step exists only for the generic Wheel and Custom templates.
  - Steps are ordered by their number (`StepDevice` … `StepFinish`). The XAML shows each step's panel through `IntEquals` with the constant (`{x:Static local:DeviceWizardViewModel.StepKind}`; `ui` is SimHub's prefix there), so adding a step means renumbering the constants only.
  - The dashboard picture is needed when the user leaves the kind step (`EnsurePhoto`), not while browsing the device list: detection takes a moment. It runs in the background (`SimHubCatalog.LoadDashPhotoAsync`, one task per device and session), started when the kind step opens (`DeviceWizard.PreloadPhoto`), so leaving the step rarely waits for it.
  - The wizard view loads SimHub's catalog asynchronously and hands it to the view model on the UI thread (`Dispatcher.BeginInvoke`); never rely on an `await` continuation for that, and never let an exception escape (it would end SimHub's UI thread).
- **Settings page (`UI/SettingsControl`)**, top to bottom: sidebar with the device list (drag to reorder) and "Add device" (wizard), plugin version and updates, car data status and connection help; device header (picture or icon, name, read-only type badge, Active, LED positions button for dashboards with a picture, Refresh from SimHub, duplicate, delete); the live preview with the inspector; an overlap warning; the connection card (SimHub devices); the LED wiring card; the Test card; the part switcher with per-part brightness; the feature tabs (RPM lights only for parts with a row, Flags, Proximity, ABS, Traction control, Priority). The effect editor in SimHub's LED editor (`Effect/EffectEditor`) picks device → part → matrix group.
- **Preview inspector (the settings page's "Live preview" card):** the user selects LEDs by clicking them in the preview and edits them in a 300 px panel right of it. It replaces the former LED layout and Front plate tabs: the layout itself comes from the wizard (or SimHub), and is only fine-tuned here (group name, count, start index, side, direction, feature targets; element name, type, index, static color and its part-wide switch, effect, press color, inputs, and the part-wide press switch). Overlapping start indices show as a warning under the preview. Below the test box only the feature tabs remain; the RPM tab is hidden for parts without a row (`DeviceViewModel.HasRpmTargets`), and `SettingsControl.ShowVisibleTab` moves off a hidden selected tab.
  - `UI/LedPreview` is interactive when `IsInteractive` is set: a hand cursor and hover ring, and a click (press and release on the same LED) raises `LedClicked` (`LedClickEventArgs`: `Part`, `Group` (null = empty space), `Logical`, `Physical`, `Add` for Ctrl/Shift). `SetSelection(groupIds, focusGroupId, focusLogical)` draws the selection: a dashed white ring around every LED of the selected groups and a solid ring on the clicked LED. The wizard's previews stay non-interactive.
  - **Assigning inputs:** a single button shows one input slot, a single dial two (`LedInspector.InputSlots`, `InputSlot`); "Assign"/"Change" on a slot captures the next input `InputState.Pressed` reports and replaces the slot's input (`LedInspector.StartCapture(slot)`; `InputSource` = `FreeTheLightsPlugin.Inputs`, null outside SimHub). Inputs arrive on SimHub's threads, so the inspector hands them to the page's dispatcher through `LedInspector.Post`. A capture ends with the first input, Cancel or a new selection. An input assigned to one direction of a dial is removed from the other.
  - **Per type:** the press color, the inputs and the press switch only show when every selected element can be pressed (`LedInspector.CanPress`: buttons and dials, not lights).
  - `UI/LedInspector` (one per `SettingsViewModel.Inspector`) holds the selection and the edits and never touches WPF. Clicking a front plate element selects it, Ctrl/Shift-click adds or removes elements; clicking an LED of a row, column or matrix selects the whole group. Its modes (`IsNone`, `IsElements`, `IsGroup`) pick the panel content. Edits of several elements write through to all of them; fields where they differ read null (`IsColorMixed`, `IsEffectMixed`) until changed.
  - `SettingsControl` wires the two: `LedClicked` → `Inspector.Select` (after switching `SelectedPart` to the clicked part, so the feature tabs follow), `Inspector.SelectionChanged` → `Preview.SetSelection`. The inspector follows `SelectedPart` (`SetPart` clears the selection). The panel is as tall as the preview area (`MinHeight` 420) so the card doesn't resize when the selection changes.
- **LED wiring card** (settings page, below the preview): the selected part's groups in strip order as one line (`DeviceViewModel.WiringSummary`, by start index), shown for every part except one of front plate elements only (`HasWiring`), also once its last group was removed. "Edit wiring" opens `UI/WiringDialog` with the wizard's wiring editor (`WiringEditor`, `WiringEditorView`: order by drag, direction, LED count, side, matrix options, adding and removing groups; front plate elements keep their LED numbers). While the dialog is open, `TestMode.WiringPartId` makes `DataUpdate` send `Engine/WiringPattern` for that part instead of its features: each group dim in its wiring color (red, green, blue, then yellow, magenta, cyan; `WiringPattern.Colors`, also the list's dots via `Theme.WiringColors`), a bright white dot walking its physical LEDs. Device and preview show the same frame (the preview takes the rendered frame), so a wrong order or direction is visible as a difference. Edits apply at once, like everywhere on the device page: the dialog publishes them through the page (so its autosave notices them), and the page saves when the dialog closes.
- **Settings page refresh:** two paces. A `DispatcherTimer` (10 Hz, background priority) publishes changed settings to `RenderDevices`, lets the preview check for layout changes (`LedPreview.Update`, which builds a layout signature) and refreshes the status texts. `CompositionTarget.Rendering` (once per screen frame) calls `LedPreview.RefreshFrames`, which repaints only when the game loop stored a new frame array (reference comparison), so animations run at SimHub's update rate. A layout change builds a new `PreviewLayout` (geometry only: spots, labels, backdrop, size; tested in `PreviewLayoutTests`). Keep per-frame work out of the timer and the timer's heavy work (JSON, signatures, text formatting) out of the per-frame path; labels' `FormattedText` is cached per layout.
- **Checking UI changes without SimHub:** use `tools/harness.sh` (see `tools/README.md`); look at the PNGs and check its output for binding errors. How it works, for extending it:
  - A net48 exe compiled with Roslyn's `csc.exe` from the MSBuild folder (`tools/build.sh`), loading the plugin and SimHub DLLs by reflection.
  - Resolve SimHub assemblies through `AssemblyResolve`.
  - Merge the same dictionaries as SimHub's `App.xaml` (see Theme above) into an `Application`, host the control in an off-screen `Window`, and save it with `RenderTargetBitmap`. Draw it through a `VisualBrush` with an absolute `Viewbox`; the default stretches to the content bounds, and LED glows reach past them.
  - Turn on `PresentationTraceSources.DataBindingSource` to catch binding errors: broken bindings fail silently.
  - Don't do this from PowerShell: its AssemblyResolve scriptblocks recurse and crash with a StackOverflow.

### SimHub presets (`SimHubData/`)
- **Catalog** (`SimHubCatalog`), loaded in the background at `Init` and cached:
  - **Devices and LED counts:** SimHub's `.shdevice` JSON (`DevicesDefaults`, `DevicesDefinitions/**/defaults.json`, zipped `.shdevicetemplate`s), parsed by `Settings/ShDeviceParser` into `SimHubDeviceInfo`. Only devices with at least one LED channel are listed.
  - **Brand and button layout:** SimHub's device registries (`IDeviceDescriptorsRegistry.GetDevices()`, public types) give brand and name per device type id. The layout control (`DefaultColorsEditor<Device>`) is found by following the descriptor's `Factory` delegate's IL to the control it references; name matching (`ShDeviceParser.MatchLayoutName`) is the fallback. IL reading only resolves operands; it can break with SimHub updates, which only loses layouts.
  - **Layouts:** `LoadButtonLayout` (UI thread) creates SimHub's control and reads the `DefaultButtonColor` markers: LED number (`Text`), canvas position and size, visibility (hidden markers are unused LED numbers). Marker positions are stored relative to the photo. Outside SimHub the photo's `siteoforigin` source doesn't load, so the photo is also found by SimHub's naming convention (`DevicesUI\<layout>.jpg`).
  - **Product pictures:** `DevicesLogos\<DeviceTypeId>.png`.
- **Building** (`Settings/PresetBuilder`): one part per channel. Wheel buttons come from the layout; the `leds` channel of wheels and dashboards is split into left side / top row / right side from SimHub's default profile (`SuggestedSplit`, only a suggestion). The layout is copied into the settings; "Refresh from SimHub" (`PresetBuilder.Refresh`) merges SimHub's current data and asks before removing anything.
- **Dashboard LEDs on the product picture** (`Settings/DashPhotoLayouts`, `Settings/DashLedDetector`). SimHub's dashboard pictures (`DevicesLogos`) have no LED coordinates. In this order:
  1. **Built-in list** `Settings/DashboardLayouts.json` (embedded resource): positions per device type id, reviewed by hand, with the SHA-256 of the picture they were made for. Used only when the picture's hash matches.
  2. **Detection at runtime** (`DashLedDetector.Detect`, pure: ARGB pixels in): bright or locally contrasting compact blobs, grown into lines LED by LED (gentle curves allowed); the highest row in the upper part, the outermost column on each side. It only answers with exactly the device's LED count and a mirror-symmetric layout (otherwise buttons on wheel pictures line up as false dashboards).
  3. **Placed by the user:** the wizard's LED positions step and the device page's picture button (`UI/PhotoLedDialog`) show `UI/PhotoLedPlacer`: drag an LED; dragging the first or last LED stretches the group (`DashPhotoLayouts.Move`).
  4. **Declined:** "Generic drawing" stores `PhotoLedSource.Generic`, and the preview draws the generic dash.
  - Positions are stored per group (`LedGroup.PhotoLeds`, picture pixels, logical order) and the source in `SimHubPreset.LedPositions`. A group whose LED count changed is drawn spread over the same path (`DashPhotoLayouts.Resample`).
  - **Updating the list:** the probe `tools/dashprobe.sh` runs the detector over every SimHub dashboard, renders overlay contact sheets for review, and writes the JSON of the results. Only add entries whose overlay was checked by eye; pictures that show fewer LEDs than the device has (Conspit CSD, SimCore UD2/DS5) can't be matched and are left to the user.
- **Kind guess** (`Settings/DeviceKindGuess`): name keywords, then "has a SimHub button layout → wheel", then capabilities. Capabilities alone are ambiguous (wheels can have displays, RPM and button LEDs like dashboards).
- **Which part an effect shows:** a new effect has no device (never "the first device": that once made a dashboard show a wheel's buttons). SimHub passes each effect its parent profile (`SetParentProfile`); `EffectHelper.AssignMatchingPart` finds the SimHub device and channel owning that profile id (`SimHubConnector.FindOwner`) and picks the FreeTheLights part made for it. The effect editor names the owning SimHub device and warns, with a one-click fix, when the effect shows a device made for another one.
- **SimHub setup** (`SimHubConnector`, JSON logic in `Settings/SimHubProfiles`): finds the user's SimHub devices with the preset's type id (`PluginManager.GetPlugin<DevicesPlugin>().GetDevices()`), checks the active LED profile of each part's channel for `{ "ContainerType": "FreeTheLights.Effect.FreeTheLightsEffect", "DeviceId", "PartId" }`, and on Connect (after confirming, with a backup of SimHub's device settings in `PluginsData/Common/FreeTheLights/backups`) writes through `DeviceInstance.SetSettings`, then reads it back to verify.
  - **Never change profiles FreeTheLights didn't create** (the user's or other plugins'). Connect (`SimHubProfiles.PlanConnect`/`Connect`) only edits FreeTheLights' own profile: it uses it when active, else makes it active, else creates it ("FreeTheLights: <device>[ / <part>]", copying only the neutral settings of the active profile: no effects, game/car binding or scripts) and makes it active. Own profiles are recognised by the ids in `DevicePart.SimHubProfileIds` (cleared when a part is copied) or by their name.
  - SimHub can switch profiles per game (`ProfileSwitchingMode`, profiles with a `GameCode`); a game-bound profile may take over again while that game runs.
  - **Two JSON shapes:** saved device files and `.shdevice` defaults wrap the channels in `"Settings"` (`{ "Settings": { "LEDS": { "leds": … } } }`), but `DeviceInstance.GetSettings` returns only that inner object: `{ "LEDS": …, "LCD": … }` for composite devices (one key per component), `{ "buttons": … }` for others. `SimHubProfiles` accepts both; test with the runtime shape, not just with files.
